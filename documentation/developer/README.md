# Plugin Developer Guide

This directory is for developers who want to write plugins for Terminal Chat. After reading it you should be able to: decide which kind of plugin to write, implement the plugin's FFI entry points, call core library hooks to register commands/menus/forms/sidebar/status bar, and load and verify it locally.

## Two plugin kinds

A plugin is a dynamic library compiled as a `cdylib`, loaded by the host through `libloading`, and communicating across the boundary with a C ABI (`safer-ffi`). There are two kinds, by where they run:

| Kind | Runs in | Responsibility | Reference implementation |
| --- | --- | --- | --- |
| **Client plugin (cli plugin)** | `cli` host process | Provides commands, menu/form/sidebar/status-bar registration, local and remote interaction, completion candidates | `crates/plugins/cli-standard` (full); `crates/plugins/example` (minimal scaffold) |
| **Server plugin (srv plugin)** | `srv` host process | Registers channels and handlers; handles chat/call/file and other server-side business | `crates/plugins/srv-standard` |

## Core concepts

- **Host**: the `cli` / `srv` binary itself. It loads the core library and plugins and dispatches commands/packets to plugins.
- **Core library (core)**: `cli-core` / `srv-core`, also a cdylib. It exposes a set of **hooks** (registration primitives + query/state functions) to plugins. During `on_init_plugin`, a plugin uses these hooks to register its commands and UI into the registries.
- **Plugin metadata (`PluginMetadata`)**: the struct a plugin reports to introduce itself to the host. It carries the name, dylib name, command name, command YAML, version, author, compatible version range, and more.
- **Command description (`command_yaml`)**: declares the command name, arguments, subcommands, aliases, and help text in YAML. The host builds command-line parsing and completion from it; the command skeleton can be generated by `cmd-gen`.
- **Registry-driven UI**: the host embeds no plugin-specific menu/sidebar knowledge. A client plugin calls hooks such as `register_menu_item` / `register_form_spec` / `register_side_section` during initialization; the host TUI renders only from the registries.

## Learning path

1. Read [plugin-contract.md](plugin-contract.md) first: which functions a plugin must export, what each metadata field means, and the dylib/command naming conventions.
2. Then read [hooks.md](hooks.md): look up the available core hook signatures and purposes by group.
3. Follow [guide.md](guide.md) to scaffold a minimal cli plugin from scratch and load it locally.
4. For server-side business, compare `srv-standard` with the "server hooks" section in hooks.md.

## Prerequisites

- Rust basics; familiarity with `cdylib`, `extern "C"` FFI, and the `unsafe` boundary.
- Understand `safer-ffi`'s `Out<T>` output parameter, `TaggedOption` optional type, and `safer_ffi::String`/`Vec`.
- Command parsing is based on `clap`; the command YAML is converted into a clap `Command` by `yaml2cmd`.

## Key constraints (avoid pitfalls)

- Structs crossing the FFI boundary must be `#[derive_ReprC] #[repr(C)]`. Under the current `safer-ffi` version, a ReprC struct **cannot embed a `Vec`** (`String` is opaque); complex lists are always returned as flat record lines through `Out<Vec<String>>`.
- Hook business arguments are always passed by reference: strings as `&safer_ffi::String`, numbers as `&i32`; output goes through `Out<'_, T>`.
- Function-pointer deduplication compares with `std::ptr::fn_addr_eq`; you cannot compare raw pointer values directly.
- Do not `dlclose` a library that is still executing on plugin unload (later instructions would land in an unloaded code page and fault). After the registry entry is removed the command stops working; the handle is released when the process exits.
